# 任务中心逻辑重构方案

依据 4.1–4.7 规范，重构小程序端任务中心（`src/routes/m.health.index.tsx` + 详情页 `m.health.$id.tsx`），并补充 PC 端必要的反馈处理入口。该规范信息量大，分阶段交付。

## 阶段 1：任务列表（小程序）—— 分类与可见范围

文件：`src/routes/m.health.index.tsx`

**1. Tabs 改为按规范 7 类**
- 全部 / 待审批 / 待响应 / 进行中 / 已完成 / 已驳回 / 已终止
- "待响应"仅在该用户作为外部执行人（如修蹄工）时显示有数据；其余角色该 tab 为空态

**2. 任务数据模型扩展**
```ts
type Status = "待审批" | "待响应" | "进行中" | "已完成" | "已驳回" | "已终止";
type Kind = "健康" | "损耗" | "修蹄" | "免疫" | "干奶" | "产后" | "驱虫" | "普修" | "复查" | "取药" | "用药";
type Relation = "我建单" | "我审批" | "我执行";
type Task = {
  ...,
  relation: Relation[],     // 当前用户与该任务的关系
  hasFeedback?: boolean,    // 有反馈待处理
  needSupply?: boolean,     // 损耗：是否申请补给
  linkedTaskId?: string,    // 关联工单（终止后新建）
};
```

**3. 可见范围过滤**
- 仅展示 `relation` 与当前用户匹配的任务
- 顶部增加次级筛选："全部 / 我建单 / 我审批 / 我执行"

**4. 卡片右下角操作文案按规范**
- 待审批 + 健康/执行类 → "前往 PC 端审批"（灰色提示文案，不可在小程序操作）
- 待审批 + 损耗类 → "去审批"（品牌色，可点击）
- 待响应 → "去接单 / 拒绝"
- 进行中 + 我执行 → "去填执行记录"
- 有反馈待处理 → 角标"反馈待处理"

## 阶段 2：任务详情（小程序）

文件：`src/routes/m.health.$id.tsx`

**1. 健康/执行类待审批**
- 展示完整审批信息（事项、对象、提出人、建议处置）
- 底部固定栏：醒目提示"健康/执行类正式审批需在 PC 端完成"+ 复制链接按钮

**2. 损耗类审批**（小程序可操作）
- 展示损耗物资、数量、估损、附件、是否申请补给
- 上报人选"申请"：审批人决策 2 步——
  1. 是否认可耗损（通过/驳回）
  2. 若认可且需申请：是否通过物资申请（通过 → 流入上报人任务池；不通过 → 通知）
- 上报人选"不申请"：仅 1 步认可/不认可
- 在小程序提供完整决策 UI

**3. 执行记录 + 反馈标注（双轨）**
- 中部"执行记录"区：按任务类型动态字段（取药/用药/修蹄/干奶/免疫/产后/驱虫/普修/复查）
- 底部"反馈标注"区：始终可展开，独立于执行记录
  - 仅执行者可见输入；提交后卡片打"反馈待处理"标
  - 反馈提示文案："反馈处理仅在 PC 端进行，处理结果会同步通知"
- 历史区显示反馈处理结果（已知悉 / 要求补充 / 重新编辑 / 终止 / 终止后新建工单）+ 关联旧/新工单链接 + 备注

## 阶段 3：PC 端反馈处理（最小实现）
